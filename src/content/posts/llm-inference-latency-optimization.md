这篇记录一次内部问答服务的优化过程。之所以值得写出来，不是因为最终结果（P99 从 4.2s 降到 1.6s），而是因为**前两个方案都判断错了**，而错误的判断过程比正确答案更有参考价值。

## 问题现状

服务上线三个月后，用户反馈「有时候要等很久」。监控数据：

| 指标 | 值 |
| --- | --- |
| QPS | 11.3 |
| 平均延迟 | 1.1 s |
| P50 延迟 | 0.8 s |
| P99 延迟 | 4.2 s |
| GPU 利用率（nvidia-smi） | 78% |
| 单卡显存占用 | 21.4 GB / 24 GB |

平均延迟和 P50 都还能接受，但 P99 是 P50 的 5 倍多。这种长尾形状说明问题不是「整体算得慢」，而是**部分请求被卡住了**。

## 第一次误判：以为是 GPU 算力不够

最直觉的判断是 GPU 打满了。78% 的利用率加上 21.4/24 GB 的显存占用，看起来确实像资源瓶颈，当时的结论是加卡。

这个判断错在**误读了 GPU 利用率的含义**。`nvidia-smi` 的 utilization 指的是「采样周期内有至少一个 kernel 在执行的时间比例」，它完全不反映 SM 的实际占用率。一个只用了 5% SM 的小 kernel 持续跑着，利用率也会显示 100%。

换用 `nsys` 做时间线分析后，真实情况是：

| 阶段 | 占单请求耗时 | 说明 |
| --- | --- | --- |
| Prefill 计算 | 18% | 真正的矩阵运算 |
| Decode 计算 | 31% | 逐 token 生成 |
| 等待批次组装 | 39% | **请求在队列里等其他请求凑批** |
| 显存分配 / 拷贝 | 9% | KV Cache 申请与释放 |
| 其他 | 3% | 序列化、日志等 |

将近 40% 的时间花在等待凑批。加卡完全解决不了这个问题——每张卡都会同样地等。

> 教训：**利用率高不等于算力饱和**。判断 GPU 是否真的是瓶颈，要看 SM 占用率（`sm__throughput`）和显存带宽利用率，不能只看 `nvidia-smi` 的那个百分数。

## 第二次误判：以为是批处理窗口太长

既然在等凑批，那把等待窗口从 100ms 调到 20ms 不就行了？

调了之后 P99 从 4.2s 降到 3.6s，但 QPS 从 11.3 掉到 7.9。这是一次典型的**指标互换而非优化**：批次变小了，单请求等待时间短了，但 GPU 每次计算处理的请求少了，整体吞吐掉了三成。

问题的本质不在窗口长度，而在**静态批处理这个模式本身**。静态批处理要求一批里所有请求一起开始、一起结束。而 LLM 生成的输出长度差异极大——同一批里有的请求生成 20 个 token，有的生成 800 个，短的必须等长的算完才能返回。

这才是长尾的真正来源：**P99 请求的延迟由它所在批次中最长的那个请求决定**。

## 真正有效的三处改动

### 1. 换成连续批处理（continuous batching）

连续批处理在每个 decode step 结束后检查：有请求生成完了就立刻返回并释放槽位，有新请求就填进空槽。请求不再需要等整批结束。

```python
# 静态批处理：整批同步推进，短请求被长请求拖住
def static_batch_loop(requests: list[Request]) -> None:
    batch = collect_until_full_or_timeout(requests, size=16, timeout_ms=100)
    while any(not r.finished for r in batch):
        forward_step(batch)          # 已完成的请求仍占着槽位空转
    for r in batch:
        r.respond()

# 连续批处理：逐 step 调度，完成即出、空位即补
def continuous_batch_loop(queue: RequestQueue) -> None:
    running: list[Request] = []
    while True:
        # 有空槽就立刻补新请求，不等超时
        while len(running) < MAX_BATCH and queue.has_pending():
            running.append(queue.pop())

        forward_step(running)

        finished = [r for r in running if r.finished]
        for r in finished:
            r.respond()              # 生成完立即返回
            release_kv_cache(r)       # 立即释放显存
        running = [r for r in running if not r.finished]
```

这一处改动贡献了最大的收益：P99 从 4.2s 降到 2.3s，同时 QPS 从 11.3 涨到 19.6。**延迟和吞吐同时改善**，说明这次动的是真正的瓶颈，而不是在做权衡。

### 2. 用 PagedAttention 解决显存碎片

连续批处理带来一个新问题：请求频繁进出，KV Cache 的申请释放变得极其零碎。原来按最大序列长度预分配连续显存的做法，会产生大量无法利用的碎片。

实测显存有效利用率只有 54%——也就是说 21.4 GB 里有将近 10 GB 是碎片。

PagedAttention 把 KV Cache 切成固定大小的 block（类似操作系统的分页），通过 block table 做逻辑到物理的映射，物理上不要求连续：

| | 改造前 | 改造后 |
| --- | --- | --- |
| 显存有效利用率 | 54% | 89% |
| 最大并发请求数 | 16 | 42 |
| 显存占用 | 21.4 GB | 20.8 GB |

并发数从 16 提到 42，批次更大，吞吐进一步上升。

### 3. 把 tokenizer 移出请求主路径

前两步做完后重新采样，发现还有个不起眼的固定开销：tokenizer 在 Python 主线程里同步执行，长输入（8k+ token）的分词要 80–120ms，而且会阻塞 GIL，连带影响同一进程内其他请求的调度。

改成独立进程池处理后，主路径上的这部分开销降到 5ms 以内。

## 最终结果

| 指标 | 优化前 | 优化后 | 变化 |
| --- | --- | --- | --- |
| QPS | 11.3 | 24.7 | +119% |
| P50 延迟 | 0.8 s | 0.6 s | −25% |
| P99 延迟 | 4.2 s | 1.6 s | **−62%** |
| 显存有效利用率 | 54% | 89% | +35pp |
| 最大并发 | 16 | 42 | +162% |
| GPU 数量 | 4 | 4 | 不变 |

没有增加任何硬件。

## 复盘：两次误判的共性

两次判断错误的根源是同一个——**用了错误的观测指标就急着下结论**。

第一次看 `nvidia-smi` 的利用率，那是个几乎无法反映真实算力占用的数字。第二次看到「在等凑批」就去调窗口参数，没有再往下问一层「为什么必须等」。

有效的做法是把观测做到能定位到具体代码路径的粒度再动手。这次真正起作用的是 `nsys` 的时间线——它直接给出了每个阶段的耗时占比，误判空间小得多。

> 一个可复用的判断准则：**如果一个改动让某个指标变好、另一个变差，那大概率没找到真正的瓶颈**，只是在做取舍。真正命中瓶颈的优化，通常是多个指标同时改善。
